# LLM-Brain v0.4.0 release review

## Outcome

Version 0.4.0 upgrades canonical memory to Google Open Knowledge Format v0.2 and storage schema 3, adds automatic host integration and provides a callable, transactional upgrade workflow with verified rollback.

The user experience is passive: users do not have to remember or request LLM-Brain during ordinary project work. LLM-Brain itself is active infrastructure loaded through each host's native skill, hook or context mechanism.

## Issues and root causes

| Issue | Classification | Root cause | Remediation |
|---|---|---|---|
| A local Codex marketplace rejected the Git marketplace refresh command. | Release defect exposed by a local configuration | The updater treated every Codex marketplace as Git-backed and did not carry source type through the upgrade plan. | Host inventory now records source type. Local sources are atomically replaced from the verified plugin archive; Git sources use Codex's native refresh. |
| Plugin hosts were offered the standalone release archive. | Release defect | Artefact selection was unconditional instead of host-aware. | Codex, Claude and Gemini use the polyglot plugin archive; standalone installs use the standalone archive. The selected artefact kind is included in the deterministic plan. |
| Failed Codex or Claude inventory could silently fall back to standalone detection. | Release defect | Detection deliberately discarded package-manager errors. | Inventory failures now abort preflight. Fallback occurs only when inventory succeeds and LLM-Brain is not installed in that host. |
| Git-backed Codex inventory may omit the installed package path. | Host integration mismatch | The updater assumed every package-manager inventory record supplied a filesystem path. | A validated fallback resolves Codex's versioned plugin cache and fails closed when the expected cache is absent. |
| Host manifests described LLM-Brain itself as passive. | Documentation and release-metadata defect | “Passive” was used for both the user's interaction burden and the solution's operating model. | Manifests now say “automatic”; documentation states that the infrastructure is active while the user experience is passive. |
| Local installation and a pushed branch existed without a public GitHub Release. | Release-process defect | Source, package, installation, vault migration and publication were treated as if they were one state. | Release proof now separately requires public branch state, tag identity, GitHub Release assets and a checksum-resolving public upgrade preflight. |

The unresolved historical source-custody gaps reported by vault preflight are vault-data limitations, not OKF v0.2 or package defects. Migration preserves and reports them rather than inventing provenance.

## Verification

- Bash syntax and repository self-checks.
- OKF v0.2 and schema-3 lifecycle regression checks.
- Transactional upgrades from schemas 1 and 2, including two registered vaults.
- Injected dependency, package, staging, cutover, unexpected-exit and final-verification failures with rollback checks.
- Local and Git Codex command selection, missing-cache refusal, failed-inventory refusal, Claude update and Gemini extension-update stubs.
- Skill and polyglot plugin validation.
- Deterministic plugin and standalone archives, checksum verification and packaged-version equality.
- Public-payload scan for machine-specific paths, private-network addresses and personal identifiers.

Fresh native Claude and Gemini session proof requires those hosts to be installed. Stubbed package-manager tests verify the release commands but do not misrepresent unavailable live-host acceptance.

## Lessons learned

1. Treat source, build, package, install, vault migration, runtime proof and public release as separate states with separate evidence.
2. Use the package manager's real inventory shape in regression fixtures, including omitted optional fields.
3. Select release artefacts from the target host, not from the development checkout.
4. Fail closed when host identity, source type or package location is uncertain.
5. Reserve “passive” for the user's experience; describe the operating model as automatic and active.
6. Preserve unresolved custody facts through migration. Missing evidence must remain visible until recovered or explicitly finalised under policy.
